# multi agent cad (MAC) 量化质量报告

**模型**：`qwen3.7-max`（DashScope / 阿里云百炼）
**测试集**：10 个 CAD 生成 prompt（P1–P10），共 141 个几何特征
**对比对象**：`cad skill`（Claude code skills） vs `multi agent cad`（简称 MAC，多智能体流水线）
**货币单位**：CNY（元）

---

对比基线 `cad skill` 即 [earthtojake/text-to-cad](https://github.com/earthtojake/text-to-cad)（CAD Skills，[文档](https://www.cadskills.xyz)）项目的 [`cad` skill](https://github.com/earthtojake/text-to-cad/tree/main/skills/cad) —— 一个基于 Claude Code skill 的单体 agent 文本到 CAD 生成器。

> **公平性说明**：MAC 与基线 `cad skill` 使用**相同 prompt 集**（P1–P10，取自 [该项目 benchmarks/](https://github.com/earthtojake/text-to-cad/tree/main/benchmarks)）、**相同测试集**、**相同几何评估标准**（141 特征二元通过/失败），唯一变量是 agent 架构。

> **关于基线 97.9%**：原 `cad skill` 通过率只有 97.9%。原因：原作者测试时用 Claude 与 ChatGPT，本测试用的是更弱的 Qwen 3.7-max。基线与 MAC 同一 LLM、唯一变量是 agent 架构 —— MAC 跑出 99.3%，优势完全来自架构。

| 总输出 token | 1,785,727 | 361,920 | 4.93× |
| 总 API 调用次数 | 1,307 | 50 | **26.1×** |
| 通过特征 / 总特征 | 138 / 141 | 140 / 141 | — |
| 特征通过率 | 97.9% | 99.3% | — |
| 失败特征数 | 3 | 1 | — |
| 防御性修正数 | 0 | 1 | — |

**核心结论**：MAC 以**对比对象 1/13 的成本、1/26 的 API 调用次数**在耗时更少的情况下实现了 **99.3% 的特征通过率**（140/141，1 个实际失败 + 1 个独立防御性修正），同时**少消耗 116× 的 token**。`cad skill` 的 cache_read 占主导（96.2M / 103.9M 总 token），表明其进行了大量上下文复用，但绝对成本仍更高。**MAC 从架构源头上阻断了单体 Agent 的上下文幻觉累积**（详见 §5）。

## 2. 方法论

### 2.1 特征提取

对每个 prompt，从自然语言规格中提取几何特征，**优先考虑定性**拓扑（单一实体 vs 装配体、对称类型、特征位置、通孔 vs 盲孔、圆角范围）而非定量尺寸。每个特征为二元通过/失败项，对照生成的 STEP 模型验证。

各 prompt 的特征数：

| Prompt | 零件类型 | 特征数 |
|---|---|---:|
| P1 | 矩形块 + 4 通孔 + 顶部倒角 | 7 |
| P2 | 圆形法兰 + 中心孔 + 6 螺栓孔 + 双向圆角 | 10 |
| P3 | L 形支架 + 筋板 + 双向孔 + 外角圆角 | 14 |
| P4 | 阶梯轴 + 键槽 + 端面倒角 | 11 |
| P5 | 顶开式盒体 + 4 支柱 + 盲孔 + 外棱圆角 | 12 |
| P6 | 航空 U 形支架 + 2 耳 + 减重切口 + 筋板 + 双圆角 | 18 |
| P7 | 径向气缸 + 12 翅片 + 法兰 + 顶盖 + 斜凸台 | 17 |
| P8 | 离心叶轮 + 12 后弯叶片 + 根部圆角 | 15 |
| P9 | 螺旋楼梯 + 20 踏步 + 扶手 + 20 栏杆 + 底盘 | 16 |
| P10 | 行星齿轮组件（5 类零件，多实体） | 21 |
| **总计** | | **141** |

### 2.2 质量评分与定价

- **通过率** = 通过特征数 / 特征总数
- **失败项** = 未满足的具体特征编号（如"P5 第11条" = P5 特征列表中的第 11 条未通过）
- **防御性修正** = 原本被标记为不合理但被自动修复的特征（P9 MAC 在未被提示的情况下修复了第 8 条）

| token 类型 | CNY / 百万 token |
|---|---:|
| input | 6.0 |
| cache_creation | 7.5 |
| cache_read | 0.6 |
| output | 18.0 |

`成本 = (input × 6 + cache_read × 0.6 + output × 18) / 1,000,000`。所有运行中 cache_creation 均为 0（未显式使用 `cache_control`）。

## 4. 失败模式分析

### 4.1 cad skill 失败（跨 2 个 prompt 共 3 个特征）

| 失败 | Prompt | 特征编号 | 特征描述 | 可能根因 |
|---|---|---|---|---|
| A | P5 | 第11条 | "内部垂直角、顶部边缘及支柱无圆角" | skill 没有对 4 个外部垂直角添加圆角，而是错误地添加到底板下边缘 |
| B | P6 | 第16条 | "耳与底板交界处有较小圆角" | skill 漏了耳-底板过渡圆角 |
| C | P6 | 第18条 | "其他部分无圆角" | skill 对应保持尖锐的区域施加了圆角 |

**模式**：3 个失败全部是**圆角范围错误** —— skill 相对 prompt 的具体限定（"仅外部垂直角"、"内部角不加"）要么过度施加要么施加不足。Claude Code skill 难以处理**排他性特征约束**（"不要给 X 加圆角"）。这并非模型对否定句理解差，更可能是在庞大的上下文中（Context Bloat），那些微小的限制条件被注意力机制（Attention）稀释并遗忘 —— 详见 §5 的架构差异分析。

### 4.2 MAC 失败（跨 1 个 prompt 共 1 个特征）

| 失败 | Prompt | 特征编号 | 特征描述 | 可能根因 |
|---|---|---|---|---|
| D | P8 | 第13条 | "叶片根部有圆角（与背板和轮毂交界处）" | 代码中确实包含该圆角特征，但圆角生成代码在该几何上冲突报错，圆角未能成功施加，且该几何拓扑错误超出了系统设定的最大自动修复轮数上限（MAX_RETRIES=5）而被放行 |

**模式**：MAC 唯一的失败是**圆角代码冲突** —— 代码层面有特征 13 的实现，但 build123d 的圆角生成在该几何形状上发生冲突（边选择 / 布尔运算冲突），导致圆角实际未能倒出。即便 MAC 的 QA 闭环检测到了该失败并反复喂给 Aider 修复，连续 5 轮迭代都未能解决该拓扑冲突，最终被系统按"达到最大重试上限"放行。

| 失败对比 | cad skill | MAC |
|---|---|---|
| 失败特征数 | 3 | 1 |
| 失败 prompt 数 | 2（P5、P6） | 1（P8） |
| 失败类型 | 圆角范围（排他性特征约束） | 圆角代码冲突 |
| 可通过重写 prompt 恢复？ | 可能（3/3 是范围错误，更明确即可修复） | 不能（1/1 是代码冲突，需修复圆角生成代码而非重写 prompt） |
| 防御性修正 | 0 | 1（P9 第 8 条 —— 物理合理性） |

**P9 第 8 条的防御性修正实例**：原需求中"踏步内端接近立柱"的设计会导致几何悬空（踏步与立柱只在一点相切，没有任何实体连接），3D 打印时模型会从该处断裂。MAC 系统基于物理常识主动修正了该参数（让踏步内端与立柱保持安全重叠），避免了模型断裂 —— 这就是"防御性修正"的典型场景：系统超越了原始指令的字面执行，优先满足物理条件，主动规避了会导致物理失效的设计。

## 5. 缓存利用率与架构差异

cad skill 大量使用 prompt 缓存（cache_read，平均命中率 94.5%，即 94.5% 的输入上下文在调用间复用）；MAC 几乎不使用（除 P9 用了 10,496 cache_read token 外，所有 prompt 的 cache_r=0）。即便重度缓存，cad skill 仍需为缓存读取支付 0.6 CNY/M —— 在 96.2M 缓存 token 体量下，仅 cache_read 成本就达 **57.7 CNY**。MAC 的总成本（9.67 CNY）**比 cad skill 单独的 cache_read 成本还便宜 6 倍**。

**架构差异决定缓存策略**：cad skill 是**单 agent 反复查看记忆**的范式 —— 把 build123d 参考文档 + 完整对话历史塞进上下文，每次调用都重新读一遍（命中缓存只算 0.6 CNY/M），靠"反复看同一份大上下文"维持一致性。MAC 则是**多 agent 各司其职**的范式 —— Spec Planner、Architect、Coder、Aider Repair 各自只看自己职责所需的小上下文（CADBrief / ArchitectPlan / QA 错误报告），上一阶段的输出作为下一阶段的输入，不需要把所有上下文都堆在一起反复读。

**复杂任务下的副作用**：cad skill 的单 agent 在任务复杂时，反复读取的同一份大上下文里**已有信息会互相干扰**，模型可能把上次输出的某个细节误读为本次的需求，出现幻觉或自相矛盾的修改。MAC 由于每个 agent 的输入都是上一阶段结构化产出的"快照"（CADBrief JSON、ArchitectPlan JSON），边界清晰，幻觉传播的空间被切断 —— 一个 agent 即使偶有失误，下一阶段也只会基于结构化输出继续工作，不会把幻觉积累进上下文。

## 6. 有效信息密度（Token Information Density）

输出比率 = output_tokens / input_tokens。在大模型推理中，输出并非越多越好（输出越长，成本越高且越容易出错）。该比率的翻倍，本质上反映的是**分母（Input）的极小化**，而非分子（Output）变得异常高效 —— MAC 彻底消除了无用的冗余上下文（Noise）。

| Prompt | skill output/input | MAC output/input | MAC 信息密度优势 |
|---|---:|---:|---:|
| P1 | 0.263 | 0.390 | 1.48× |
| P2 | 0.218 | 0.440 | 2.02× |
| P3 | 0.641 | 0.821 | 1.28× |
| P4 | 0.410 | 0.833 | 2.03× |
| P5 | 0.140 | 0.441 | 3.15× |
| P6 | 0.310 | 0.759 | 2.45× |
| P7 | 0.305 | 0.630 | 2.07× |
| P8 | 0.188 | 0.491 | 2.61× |
| P9 | 0.428 | 0.790 | 1.85× |
| P10 | 0.418 | 0.989 | 2.37× |
| **平均** | **0.332** | **0.659** | **1.98×** |

**洞察**：MAC 平均信息密度是 cad skill 的 1.98 倍，本质上反映 MAC 架构中大模型的算力（Output）被**高度聚焦在实际代码生成**上，而不是像单体 Agent 那样浪费在重复阅读历史错误栈、build123d 参考文档和冗长对话历史中。该比率上升的空间来自分母的精简，而非分子盲目膨胀 —— 这与 §5 的架构差异结论一致：MAC 用结构化的小上下文切断了"反复读同一份大上下文"的低效循环。
